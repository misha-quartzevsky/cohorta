### Три главных риска
1. **Потеря данных одним запросом (A-1).** `DELETE /api/collections/users/records/<я>` проходит (204), в обход 14-дневного удаления и защиты «передай группу»: сносятся группа и **экзамены её участников**; лекции удалённого остаются в базе без владельца. Чужие экзамены страдают, если их авторы вступили в группу этого пользователя (ссылку открывает владелец).
2. **Утечка ответов на билеты (B-1).** Ответ срезается только в ответе API; `filter=answer~"абв%"` восстановил ответ целиком побуквенно под рядовым участником группы. Защита Proof-of-Knowledge не работает (нужно быть членом группы; утекает учебный контент, не ПДн; для не-групповых экзаменов оракул по коду должен работать так же, не проверялось).
3. **XSS на конспектах (C-1).** Копия чужой лекции переносит HTML как есть и показывается без очистки: `onerror` выполнился, из `localStorage` читается токен PocketBase. CSP на фронтенде нет (C-6), поэтому токен можно отправить на любой хост.

Отдельно: на **проде** дыр больше (раздел 7), а публичные документы описывают их пошагово (D-4).

## 3. Находки (по убыванию серьёзности)

### P0

**A-1. Прямой DELETE пользователя обходит 14 дней и каскадом сносит чужие данные.** Воспроизведено.
- Где: `users.deleteRule = id = @request.auth.id` (заводское, в миграциях не менялось). Каскады: `groups.owner` — `pb_migrations/1787610000_created_groups.js:92` (`cascadeDelete: true`); `exams.group` — `1790010000_group_schema.js:144` (`cascadeDelete: true`); `exams.owner` — `1787400000_created_exams.js:97`. Хука `onRecordDelete*` для `users` нет; штатная защита — только маршрут `account_deletion.pb.js:21-38`.
- Сценарий (песочница): владелец группы с участником вызвал штатный `POST /api/account/delete-request` → 409 `group_owner`. Затем `DELETE /api/collections/users/records/<я>` → **204**. Группа → 404, **экзамен участника группы → 404** (снесён каскадом), лекция удалённого осталась с `owner=""`.
- Исправление: `users.deleteRule = null` (удаление только маршрутом и кроном); хук-страховка `onRecordDeleteRequest`; `exams.group` перевести на `cascadeDelete: false`; запретить/передавать группу владельца с участниками. Размер M. Миграция: да. Прод: зависит от выкатки (поле `exams.group` появляется с 1790010000, `users.deleteRule` на проде такой же).

**B-1. Ответы группового экзамена читаются через `filter`/`sort` по `answer`.** Воспроизведено.
- Где: срез в `pb_hooks/exam_pok.pb.js:25-57` (`e.record.set("answer", "")` на `:46`, `:49`) выполняется после выборки; поле `answer` не скрыто (`1787400100_created_exam_tickets.js:105-110`), чтение общего списка открыто члену группы (`1790010000_group_schema.js:35-36`, `:59-65`).
- Сценарий (песочница): `H` — рядовой участник. Прямое чтение: `answer=""` (срез работает). `GET .../exam_tickets/records?filter=(exam="E" && number=1 && answer~"секрет%")&fields=id` → 1 запись; `answer~"zzz%"` → 0. Побуквенный подбор по алфавиту восстановил ответ целиком: «секретныйответфеникс» = исходный. `sort=-answer` принимается (200). `expand=exam_tickets_via_exam` ответ срезает (`""`).
- Исправление: фильтры на стороне запроса не заткнуть. Вынести `answer`/`attachments` в отдельную коллекцию с правилом «владелец экзамена или автор» (или закрыть list/view для не-владельцев и отдавать вопросы маршрутом); срез оставить вторым слоем. Размер L. Миграция: да; затронуты клиент, `take-my-answer`, подгруппы.

**C-1. Хранимый XSS: копия чужой лекции без очистки.** Воспроизведено.
- Где: `pb_hooks/lecture_sharing.pb.js:177` (`copy.set("content", String(lecture.get("content") || ""))`) — серверной очистки нет; рендер копии: `apps/web/src/pages/LectureView.tsx:492` (`dangerouslySetInnerHTML={{ __html: content || "" }}`, режим `static` по умолчанию, `:93-94`) без `sanitizeHtml`. Остальные места без очистки: `TicketPage.tsx:267`, `CheatsheetPage.tsx:124`, `components/cards/RichCardFace.tsx:53`; с очисткой — `GroupLecturePage.tsx:216`, `GroupTicketPage.tsx:352`.
- Сценарий (песочница): автор записал в `lectures.content` через REST `<img src=x onerror="window.__xss=...">` (Tiptap обходится), выдал жертве доступ с `allow_copy=true`; жертва `POST /api/lectures/{id}/copy` → 200; на сервере в копии `onerror` сохранён. Открытие `/note/<slug>` копии в браузере: `window.__xss = "img:801"` — скрипт выполнился без клика и прочитал `localStorage.pocketbase_auth` (801 знак: токен). В общем просмотре той же лекции (`GroupLecturePage`) скрипт не выполнился (`__xss = null`).
- Последствия: токен жертвы, любые запросы от её имени (чтение/правка/удаление лекций), вызов `/api/quiz/generate`; CSP нет (C-6), токен можно отправить наружу.
- Условие: автор и жертва в одной группе, доступ с копированием, жертва нажала «Добавить в мои конспекты». Регистрация открыта, группу и доступ злоумышленник создаёт сам.
- Исправление: санитайзить на выходе во всех `dangerouslySetInnerHTML`; заменить самописный `sanitizeHtml` на DOMPurify с белым списком; чистить при записи и при `/copy` в хуке. Размер M. Миграция: нет (желательна разовая очистка существующих записей).

### 13.2. C-3: лимит ИИ считает сохранённые квизы, а не вызовы модели

Сейчас `functions/api/quiz/generate.ts:193-209` считает записи `quizzes` за сутки; генерация без сохранения лимит не тратит, параллельные запросы проходят (check-then-act), `title` не ограничен. Провайдер собираются сменить на YandexGPT: счёт должен жить вне кода конкретного провайдера.

**Вариант (а): запись попытки до вызова в PocketBase.**
- Что: коллекция `ai_calls` (`user`, `day`, `n`, `kind`, `created`). Функция до вызова модели создаёт запись с `n = текущее число + 1` и уникальным индексом `(user, day, n)`: параллельный запрос получает конфликт и отказ, а не второй вызов. Правила: создание `user = ME` (функция работает токеном пользователя), удаление и правка `null` (лимит не сбросить). Хук-cron чистит записи старше 30 дней.
- Параллельные запросы: закрыты уникальным индексом. Смена провайдера: не влияет (счёт до вызова, любое имя провайдера пишется в `kind`). Возврат попытки при сбое провайдера: решается политикой (считать все попытки проще и жёстче; не считать 5xx провайдера требует второго обновления записи).
- Стоимость и сложность: миграция + правила + 20-30 строк в функции + тест; одна запись PocketBase на вызов (десятки в сутки на пользователя: нагрузка ничтожна). Работает без платных функций Cloudflare, лимит виден в админке.
- Минус: пользователь может сам создать записи через API и израсходовать **свой** лимит (вред только себе); функция зависит от доступности PocketBase (сейчас тоже зависит: читает `quizzes`).

**Вариант (б): счётчик на стороне Cloudflare.**
- (б1) Workers KV: ключ `user:day`, значение счётчик. Чтение и запись не атомарны, KV согласуется с задержкой между точками присутствия: параллельные запросы и пользователи в разных регионах могут обойти лимит; бесплатный тариф ограничивает записи (порядка тысячи в сутки на аккаунт), что на росте упрётся. Сложность: привязка KV в `wrangler.toml`, переменные в Pages.
- (б2) Rate Limiting binding: правило «N запросов за период» на ключ (id пользователя), считает быстро и локально в точке присутствия, не точное и не суточное (периоды 10 или 60 секунд); хорошо против всплеска, плохо как суточная квота.
- (б3) Durable Object на пользователя: точный счёт без гонок, но платный тариф Workers и самая сложная схема (отдельный класс, привязка, миграции DO).
- Параллельные запросы: б1 не закрывает, б2 частично, б3 закрывает. Смена провайдера: не влияет. Стоимость: б1 бесплатно до лимитов, б2 бесплатно, б3 платно.

**Рекомендация: вариант (а)** с уникальным индексом и политикой «считать каждый вызов модели, включая повтор при невалидном ответе». Добавить в функцию ограничение длины `title` и проверку типа `text` (C-4). Для защиты от всплеска можно поверх включить б2.

### 13.3. `protected: true` у файловых полей (A-9/B-2, часть, оставленная в стороне)

Сейчас файл `lectures.file`, `deck_cards.attachments`, `exam_tickets.attachments` отдаётся любому, кто знает адрес (имя содержит 10 случайных знаков, но не секретно): отзыв доступа, выход из группы и корзина файл не закрывают.

С `protected: true` PocketBase отдаёт файл только по короткоживущему файловому токену, который выдаёт `pb.files.getToken()` вошедшему пользователю, проходящему правило просмотра записи (владелец или получатель доступа). Картинки внутри HTML лекций хранятся как `[[file:имя]]` и превращаются в адреса при показе (`resolveFileTokens`, `fileTokens.ts`).

**Вариант (а): токен в адресе картинки при показе, обновление по таймеру.**
- Что: при открытии лекции клиент запрашивает файловый токен (действует несколько минут, значение задаёт настройка `fileToken.duration`), добавляет `?token=…` ко всем адресам файлов записи и обновляет токен до истечения (по таймеру и при возврате на вкладку), переписывая `src` в DOM. Нужна единая функция вместо трёх копий (`lectureService`, `deckService`, `fileTokens.ts`).
- Что ломается: (1) страница, открытая дольше срока токена, теряет картинки, пока не обновится токен; (2) копирование картинки по адресу и открытие в новой вкладке дают ссылку, которая быстро умирает; (3) service worker и офлайн-кеш (PWA прекеширует только сборку, но картинки лекции в кеш не попадают: офлайн их и сейчас нет); (4) экспорт аккаунта (`accountExport.ts` собирает zip с файлами) должен получать токен; (5) общий просмотр лекции получателем: токен выдаётся ему, правило просмотра записи проверяет доступ получателя, подходит; (6) ранее вставленные в HTML абсолютные адреса без токена перестают открываться: нужна разовая проверка, что в базе все картинки хранятся токенами `[[file:…]]` (уже так), иначе переписать.
- Размер: M (клиент) + миграция на 3 поля (`protected: true`, `down` возвращает `false`). Риск: средний (картинки в лекциях видны постоянно: регрессия заметна сразу).

**Вариант (б): не включать `protected`, закрыть остальное.** Оставить публичные адреса с неугадываемым именем, но уже сделаны тип и размер файла (волна 1), CSP и `nosniff` (PocketBase отдаёт файлы с `Content-Security-Policy: sandbox`). Остаточный риск: тот, кто один раз получил адрес (участник группы, потом исключённый), сохраняет доступ к файлу. Для учебных конспектов без ПДн это приемлемо, пока нет требований конфиденциальности.

**Вариант (в): маршрут выдачи файла в хуке.** `GET /api/lectures/{id}/file/{name}` проверяет доступ и отдаёт файл. `<img>` не передаёт заголовок `Authorization`, поэтому нужен токен в адресе или cookie-сессия, то есть тот же вариант (а) с большим объёмом кода. Не рекомендуется.

**Рекомендация:** (б) до закрытой беты, затем (а) вместе с единым модулем адресов файлов. Если конфиденциальность файлов нужна уже сейчас, делать (а).

### 13.4. C-1: очистка HTML на сервере в `/copy` (вместо реализации в волне 1)

В JSVM нет DOMPurify, поэтому серверная очистка в `POST /api/lectures/{id}/copy` в волне 1 не добавлялась: защита стоит на выводе (`RichHtml` → `sanitizeHtml`), копия на сервере хранит HTML как есть (тест `security-xss.spec.ts` это проверяет).

Варианты на будущее: (а) ничего не добавлять: вывод всегда очищается, а редактор Tiptap при открытии копии сам режет всё, чего нет в схеме; (б) в хуке `/copy` убирать грубые признаки (теги `script`, `iframe`, `svg`, атрибуты `on*`, схемы `javascript:`) регулярным выражением: это обход-подверженный чёрный список, как прежний `sanitizeHtml`, и давать ложное чувство защиты не стоит; (в) вынести очистку в маршрут Cloudflare Function с DOMPurify и вызывать из клиента перед `/copy` (клиентская копия вместо серверной). Рекомендация: (а). Серверный слой даёт защиту только если клиент однажды забудет очистку; для этого есть тест на все места вывода (`RichHtml` единственный компонент с `dangerouslySetInnerHTML`, исключение: `ui/Icon.tsx` с константными путями иконок).
