## 2026-10-16 — CF Pages Function для квиза развёрнута и проверена на проде

Деплой Cloudflare Pages уже был подключён к GitHub (автодеплой по пушу в `main`) — настройка root directory/build/переменных окружения сделана владелицей самостоятельно по чек-листу.

Серверная функция `functions/api/quiz/generate.ts` (spec 6.1) реализована, задеплоена и проверена **живым вызовом** на проде (реальный PocketBase на Amvera + реальный ключ Gemini в Cloudflare):
- 401/400/404/422 — все пути ошибок подтверждены curl-запросами к `https://cohorta.pages.dev/api/quiz/generate`.
- 502 — обнаружена и устранена проблема с моделью (ниже).
- 200 — финальный реальный вызов вернул корректно сформированный квиз (5 вопросов mcq с объяснениями и точными цитатами из текста лекции).

**Важная находка**: модель `gemini-2.5-flash` из черновика спеки недоступна новым аккаунтам Google («no longer available to new users», подтверждено ответом API). Через временный диагностический эндпоинт (`GET` того же пути, список моделей от Google, убран после диагностики) нашли рабочую замену — **`gemini-flash-lite-latest`** (алиас на актуальную Flash-Lite, более высокий бесплатный лимit, чем у Flash). `GEMINI_MODEL` в Cloudflare и `DEFAULT_MODEL`/`.dev.vars.example` в коде обновлены на неё.

Побочный эффект диагностики: создавалась и была удалена тестовая лекция на проде (`___TMP_QUIZ_TEST___`), реальных данных пользователя не затрагивало.

**Решение на будущее**: когда тестируем Gemini не с демо-данными, а ближе к реальным пользователям — останавливаемся и спрашиваем, прежде чем тратить их квоту.

## 2026-10-19 — волна B2 (лекции и поиск)

- **Статус лекции в списке «Все лекции» (4 бейджа):** «Слабо» (danger) — у лекции есть хоть одна слабая тема (accuracy темы < 0.6, как в панели понимания); иначе по общему percent: «Повторить» (warn) — percent < 75, «Выучено» (ok) — percent ≥ 75, «Не начато» (neutral) — квиза не было вовсе. Старая формула спеки 6.4 (2 порога, другие названия/цвета) заменяется этой — подтверждено владелицей на выбор из трёх вариантов.
- **Поиск одногруппников** идёт через существующий серверный ростер `/api/groups/:id/roster` (`pb_hooks/groups_access.pb.js`, A0.5), не напрямую через коллекцию `users` — её `viewRule` с A0.5 отдаёт только свой профиль, прямой запрос к чужим профилям для поиска по имени не сработает.
- **Поиск чужих лекций** — коллекция `lecture_previews`, фильтр только по `title`. Её `listRule` (ограничена участником группы) и серверный хук (строка появляется только если автор включил предпросмотр) уже достаточны — дополнительных проверок в клиентском коде не потребовалось. Проверено запросом на локальной копии со вторым тестовым аккаунтом (4 шага: без связи → 0, в группе без предпросмотра → 0, лекция привязана к группе но предпросмотр выключен → 0, предпросмотр включён → находится 1 запись по названию, `content` в записи нет).
- **Найдено, не чинил:** `lecture_previews.preview_text` хранит фрагмент текста лекции (до 400 символов), а не только заголовок — расходится со словарём («предпросмотр — название, не текст»). Это поведение из A0.5 (хук `lecture_previews.pb.js`), не из B2; мой поиск использует только `title`, но прямой запрос к коллекции всё равно отдаёт `preview_text` участнику группы. Решение, чинить ли, за владелицей.
- **Клик по найденной чужой лекции/одногруппнику в поиске — пока не ведёт никуда** (не ссылка): «Лекция закрыта / Запросить доступ» и профиль одногруппника — экраны волны C, которой ещё нет.
- **«Новая лекция» на «Все лекции»** ведёт на `/предметы` (там уже есть «+ Добавить лекцию» у каждого предмета) — в макете целевое действие кнопки не нарисовано, не стал придумывать отдельный флоу создания лекции без выбора предмета.

## 2026-10-19 — «Добавить конспект» (прикрепить лекцию к паре постфактум)

Запрошено владелицей после приёмки первой версии B3.

- **Схема**: новая коллекция `schedule_slot_lectures` (owner, slot, lecture, date), миграция `1790003000_created_schedule_slot_lectures.js`. Резервная копия `pb_data` сделана локально перед миграцией (`pocketbase/pb_backups/backup-before-slot-lecture-links/`) — доступа к продовому диску Amvera по-прежнему нет (см. открытый вопрос 1 в PROGRESS.md), эта миграция пока накатана только локально.
- **Привязка — на одну конкретную дату, не на все повторения слота** (подтверждено владелицей: вопрос задавался явно). Чтобы на следующей неделе та же пустая пара снова предложила привязать конспект, а не молча унаследовала прошлый выбор.
- **Одна лекция может быть прикреплена к нескольким разным парам/датам одновременно** (пример владелицы: Философия вторник 4 пара и Философия четверг 2 пара) — поэтому отдельная таблица-связка, а не relation-поле на лекции (у лекции уже есть свои `slot`/`lecture_date` — её «родная» пара, не трогали).
- **`findLectureForOccurrence`** (spec 4.2) расширена необязательным параметром `links`: сначала ищет «родную» лекцию пары, при отсутствии — запись в `schedule_slot_lectures` на ту же дату. Старые вызовы без параметра работают как раньше (пройденные тесты это подтверждают).
- **Вход**: новый пункт «Добавить конспект» в меню пустой пары — на `/schedule` (десктоп-сетка и телефон, рядом с «Начать конспект») и на «Пары предмета». Открывает окно того же вида, что форма пары (`.c-dialog`), со списком лекций предмета.
