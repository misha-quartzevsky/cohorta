# Миграция на дизайн-основу — что осталось

Дата анализа: 2026-10-16. Чисто кодовый аудит (без запуска приложения), для планирования следующих шагов серии `1A.10` (`style(...): перенос ... на дизайн-основу`).

## Как устроена миграция (важно для чтения таблицы ниже)

В проекте два поколения токенов:

- **Старые** (`/DESIGN.md`, объявлены в `:root` самого `apps/web/src/App.css`): `--ink`, `--brand-1`, `--surface`, `--border`, `--success` и т.д. Это не «хардкод», но это **прошлое** поколение дизайн-основы.
- **Новые** (`apps/web/src/styles/tokens.css`, spec «1A»): `--color-ink`, `--color-canvas`, `--color-accent` и т.д. + классы `ds-*` из `apps/web/src/styles/components.css`.

Почти весь продукт — один общий файл `App.css` (6141 строк), классы в нём используют и старые, и новые страницы/компоненты. Экраны не имеют собственных scoped-CSS — поэтому «перенести экран на дизайн-основу» на практике означает **переписать его блок правил в `App.css`** (обычно по шаблону `var(--color-X, var(--ink))` — новый токен с фоллбэком на старый) и, где уместно, достать разметку на компоненты `components/ui/*`. Готовые экраны `/schedule`, `/tasks`, квиз и новая главная (виджеты `Hero`/`QuickActions` отчасти) изначально писались сразу на новых токенах.

Проверка «мигрировано/нет» в этом документе — не по наличию классов `ds-*` в `.tsx` (в легаси-экранах их и не будет, стили общие в `App.css`), а по тому, **на каких токенах держится блок правил в `App.css`**, подписанный под конкретный экран/компонент, плюс прямой grep по `.tsx` на сырой hex / инлайн-цвета / эмодзи-иконки.

Подтверждено по `git log` и факту (секции `App.css` с меткой «Перенесено на дизайн-основу 1A»): **полностью на новых токенах** — карточка лекции в редакторе (`LectureEditor`, 1A.10 шаг 1), лента лекций курса (`LecturesPage`, шаг 2), «гигиена аккаунта» (`AccountActions`, шаг 5), онбординг-мастер (`OnboardingWizard` + все `steps/*`, шаг 4 — проверено построчно, везде есть новый токен с фоллбэком). **Частично** — центр подготовки к экзамену (шаг 3): мигрированы только hero и карта билетов (`.exam-prep-hero`, `.exam-map-grid` — секции `App.css:4751/4771`), а импорт билетов и шпаргалка в той же странице — нет (см. таблицу).

## Рекомендуемый порядок (по видимости экрана и размеру блока)

1. Дашборд (самый частый экран, §7 DESIGN.md требует именно его как вход).
2. Глобальный сайдбар + шапка (видны всегда, одна правка — выигрыш на всех страницах).
3. Группа (самый большой технический долг — 106 старых обращений, но экран используется не всеми).
4. Deck-модуль (карточки) + убрать эмодзи `🧠`.
5. Остаток экзамен-модуля (импорт, шпаргалка, `ExamsPage`).
6. Вход, Privacy, точечные хвосты (TagEditor-палитра, LectureView инлайн-фоллбэк).
7. Медиа-блоки/редактор — по возможности в последнюю очередь (общий движок, более рискованная правка).
